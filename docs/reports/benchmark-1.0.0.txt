--------------------------------------------------------------------------------
 INTERPRETATION / NO-OPTIMIZATION NEEDED
--------------------------------------------------------------------------------
* revocation.IsRevoked against a 100k-entry set: ~6.6-6.8 ns/op, 0 allocs —
  a single RLocked map lookup; no change possible.
* audit.Chain.Append: 1,107 ns/op, 17 allocs — JSON canonicalisation + SHA-256
  per event; inherent to the hash chain.
* audit.Verify scales linearly O(n): 1k=0.78ms, 10k=8.0ms, 100k=78.1ms
  (~1.27M events/s verify throughput). This re-derives every digest; it is the
  correctness boundary and was not optimised away.
* store AppendSyncEveryAppend: 8.18 ms/op — dominated by one fsync + atomic
  directory-rename per record (durable by design).
* store AppendBatched (SegmentSize=256): 33.5 us/op — ~244x faster by amortising
  fsync across 256 records. The design already batches fsync; no further change
  would improve crash-consistency, so none was made.
* store ReplayVerify (10k records): 16.5 ms per reopen (JSONL decode + full
  re-hash) — acceptable for a cold-start recovery drill.
* governance FullCaseToVerdict (7-stage, 2-phase): 2.29 us/case.
* resource DepriveFullSequence (5-step incl. snapshot): 2.62 us/case.
* prison RunScenarioA in-memory: 69.8 us/journey; on FileStore: 9.81 ms/journey
  (the delta is the fsync-bound ledger close, consistent with store numbers).
* Binary is ~3.2 MB, starts in ~2.7 ms, demo/drill run in ~11 ms with <8 MiB RSS.

No before/after optimisation table is included because no correctness-changing
optimisation was warranted: the hot paths are already O(1) appends and
deliberately fsync-batched; the O(n) Verify is the tamper-detection contract.
